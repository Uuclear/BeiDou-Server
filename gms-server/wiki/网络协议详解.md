# 网络协议详解

本文档详细介绍BeiDou冒险岛服务端使用的网络协议，包括数据包结构、加密方式、登录流程、操作码等内容。

## 一、协议概述

冒险岛（MapleStory）v83版本使用**自定义TCP协议**进行客户端与服务端之间的通信，基于长连接，所有数据包都经过自定义加密处理。

### 1.1 通信架构

```
┌─────────────┐                           ┌─────────────┐
│             │    TCP 8484 (登录端口)     │             │
│   Client    │ ─────────────────────────►│ LoginServer │
│  (游戏客户端)│                           │ (登录服务器)│
│             │ ◄─────────────────────────│             │
└──────┬──────┘     返回服务器列表/频道IP   └─────────────┘
       │
       │ TCP 频道端口（如8500+）
       ▼
┌─────────────┐                           ┌─────────────┐
│             │ ◄─────────────────────────│             │
│   Client    │                           │ChannelServer│
│             │ ─────────────────────────►│ (频道服务器)│
└─────────────┘     游戏内所有交互通信      └─────────────┘
```

### 1.2 协议特点

| 特性 | 说明 |
|------|------|
| **传输层** | TCP长连接（保证可靠传输、顺序） |
| **端口** | LoginServer默认8484，ChannelServer动态端口 |
| **加密** | MapleAESOFB（AES-OFB模式）+ MapleCustomEncryption（自定义滚动加密） |
| **字节序** | 小端序（Little-Endian） |
| **包结构** | 自定义二进制包头 + 数据体 |
| **无状态？** | 否，是有状态连接，每个连接维护加密上下文 |

### 1.3 加密算法

服务端使用两层加密：

1. **MapleCustomEncryption（自定义滚动加密）**：用于加密数据包包头
   - 对包头长度字段进行滚动异或和位移变换
   - 每个包的加密密钥随包序号变化

2. **MapleAESOFB（AES OFB模式）**：用于加密数据包体
   - 基于AES算法的OFB（Output Feedback）模式
   - 使用4字节初始化向量（IV）
   - 登录阶段和频道阶段使用不同的IV常量
   - 每发送/接收一个包，IV都会按规则变换

加密相关代码位于 `net.encryption` 包：
- `MapleAESOFB.java`：AES加解密实现
- `MapleCustomEncryption.java`：自定义包头加密
- `PacketEncoder.java`：数据包编码（发送加密）
- `PacketDecoder.java`：数据包解码（接收解密）

### 1.4 版本与IV常量

不同版本的冒险岛使用不同的版本号和IV：

| 版本 | Version | WzVersion | Login IV | 说明 |
|------|---------|-----------|----------|------|
| v83 | 83 | 1 | `[0x0A, 0x73, 0x56, 0x86]` | GMS v83（本服务端目标版本） |
| v62 | 62 | 1 | `[0x07, 0x0A, 0x28, 0x63]` | 常见怀旧版本 |
| v75 | 75 | 1 | `[0x5A, 0x73, 0x64, 0x83]` | 其他版本 |

**注意**：客户端版本号必须和服务端配置一致，包括Version、WzVersion、IV常量，否则无法建立连接或会出现解密失败。

相关配置在 `constants.ServerConfig` 或配置文件中。

## 二、数据包结构

### 2.1 完整数据包格式

每个网络数据包（Packet）由**包头（Header）**和**数据体（Payload）**两部分组成：

```
┌───────────────────────────────────────────────────────┐
│                    数据包（Packet）                    │
├──────────────────────────┬────────────────────────────┤
│       包头 (Header)      │       数据体 (Payload)     │
│      固定 4 字节         │      可变长度               │
│  [长度][操作码(可选)]     │   加密后的业务数据          │
└──────────────────────────┴────────────────────────────┘
```

**注意**：
- 客户端发送给服务端的包（Recv）和服务端发给客户端的包（Send）结构略有不同
- 所有数据包在发送前都经过加密，接收后解密

### 2.2 包头结构

#### 2.2.1 发送包（Send Packet，服务端→客户端）

服务端发往客户端的数据包，包头为**4字节**：

| 偏移 | 长度 | 说明 |
|------|------|------|
| 0 | 2字节 | 包长度（大端序？不，实际加密处理） |
| 2 | 2字节 | 包头校验/加密部分（CustomEncryption加密） |

**实际处理过程**（PacketEncoder）：
1. 获取原始数据体长度，加上4字节包头，得到总包长 `length`
2. 将长度写入一个int的低16位
3. 与发送IV一起进行MapleCustomEncryption加密，得到4字节包头
4. 4字节包头后紧跟AES加密后的数据包体

#### 2.2.2 接收包（Recv Packet，客户端→服务端）

客户端发往服务端的数据包，包头同样**4字节**，但需要先解密才能得到长度：

| 偏移 | 长度 | 说明 |
|------|------|------|
| 0 | 4字节 | 加密后的包头，解密后得到包长度 |

**解密过程**（PacketDecoder）：
1. 先读取4字节包头
2. 使用MapleCustomEncryption结合当前接收IV解密包头，得到包长度
3. 根据长度读取对应字节数的数据体
4. 使用MapleAESOFB解密数据体
5. 第一个（或两个）字节是操作码（Opcode）

### 2.3 数据体结构

解密后的数据体格式：

```
┌─────────────┬───────────────────────────────────┐
│ 操作码      │          数据内容                  │
│ (1-2字节)   │   (变长，取决于操作码类型)         │
└─────────────┴───────────────────────────────────┘
```

- **操作码（Opcode）**：标识这个包的类型，决定后续数据如何解析
  - v83版本RecvOpcode通常为1字节或2字节
  - SendOpcode通常为2字节
- **数据内容**：按操作码定义的顺序排列的各种数据类型字段

### 2.4 数据类型

数据体中使用以下数据类型（以小端序排列）：

| 类型 | 长度 | 说明 | 读取方法 |
|------|------|------|----------|
| byte | 1字节 | 有符号字节 (-128 ~ 127) | `readByte()` |
| short | 2字节 | 有符号短整型 | `readShort()` |
| int | 4字节 | 有符号整型 | `readInt()` |
| long | 8字节 | 有符号长整型 | `readLong()` |
| bool | 1字节 | 布尔值（0=false，1=true） | `readBool()` |
| string | 2+N字节 | 字符串：先2字节长度N，后N字节ASCII/UTF字符 | `readString()` |
| position | 4字节 | 坐标(X:short, Y:short) | `readPosition()` |
| 特殊类型 | 变长 | 根据协议自定义结构 | 对应read方法 |

**注意**：
- 字符串：长度前缀为short（2字节），然后是字符数据，冒险岛字符串通常没有null终止符
- 坐标：两个short（X坐标，Y坐标）
- 部分包可能有填充字节、保留字节

代码中使用 `InPacket`（接收）和 `OutPacket`（发送）封装读写操作，位于 `net.packet` 包。

### 2.5 数据包示例（已解密）

以**客户端登录请求**为例（简化示意）：

```
接收包: LOGIN_PASSWORD
────────────────────────────────────
字节数:  内容:        说明:
[0]      0x01         RecvOpcode.LOGIN_PASSWORD = 0x01 (1字节)
[1-2]    len          用户名长度 (short)
[3..]    "admin"      用户名字符串
[...]    len          密码长度
[...]    "admin"      密码字符串
[...]    0x08         客户端版本标识?
[...]    0x00...      其他字段...
────────────────────────────────────
```

以**服务端登录成功**为例（简化示意）：

```
发送包: LOGIN_STATUS (登录成功)
────────────────────────────────────
字节数:  内容:        说明:
[0-1]    0x0000       SendOpcode.LOGIN_STATUS = 0x0000 (short, 0表示成功)
[2]      0x00         状态码: 0=成功, 其他=错误原因
[3-6]    accountId    账号ID (int)
[7]      gender       性别 (byte)
[8]      gmLevel      GM等级 (byte)
[...]    ...          其他账号信息、服务器列表等
────────────────────────────────────
```

## 三、操作码（Opcode）

### 3.1 什么是操作码

操作码（Opcode）是数据包中第一个（或前两个）字节，用于标识数据包的类型。服务端和客户端必须使用完全一致的Opcode映射，否则无法正确解析数据包。

- **RecvOpcode**：客户端→服务端的操作码（客户端发送什么）
- **SendOpcode**：服务端→客户端的操作码（服务端发送什么）

v83版本大约有：
- 约150+个RecvOpcode
- 约200+个SendOpcode

### 3.2 Opcode定义文件

Opcode定义在 `net.opcodes` 包中：

- `RecvOpcode.java`：接收操作码常量
- `SendOpcode.java`：发送操作码常量

示例（RecvOpcode）：
```java
public final class RecvOpcode {
    // 登录阶段
    public static final short LOGIN_PASSWORD = 0x01;
    public static final short GUEST_LOGIN = 0x02;
    public static final short SERVERLIST_REREQUEST = 0x04;
    public static final short CHARLIST_REQUEST = 0x05;
    // ...
    
    // 游戏阶段
    public static final short CHANGE_MAP = 0x23;
    public static final short CHANGE_CHANNEL = 0x24;
    public static final short MOVE_PLAYER = 0x26;
    public static final short CLOSE_RANGE_ATTACK = 0x29;
    public static final short RANGED_ATTACK = 0x2A;
    public static final short MAGIC_ATTACK = 0x2B;
    // ...
}
```

示例（SendOpcode）：
```java
public final class SendOpcode {
    // 登录阶段
    public static final short LOGIN_STATUS = 0x00;
    public static final short SERVERLIST = 0x02;
    public static final short CHARLIST = 0x04;
    public static final short SERVER_IP = 0x07;
    // ...
    
    // 游戏阶段
    public static final short WARP_TO_MAP = 0x7E;
    public static final short SPAWN_PLAYER = 0xA0;
    public static final short MOVE_PLAYER = 0xBA;
    public static final short MOB_SPAWN = 0x9E;
    public static final short CLOSE_RANGE_ATTACK = 0xAE;
    // ...
}
```

### 3.3 Opcode路由机制

服务端使用 `PacketProcessor` 进行数据包路由：

1. 解密数据包后，读取操作码
2. 根据操作码查找注册的 `PacketHandler`
3. 调用对应Handler的 `handlePacket(InPacket in, Client c)` 方法处理
4. 如果没有找到对应Handler，记录"Unknown opcode"日志

Handler注册在网络初始化时完成，每个RecvOpcode对应一个Handler类。

相关代码：
- `net.PacketProcessor`：处理器注册与路由
- `net.AbstractPacketHandler`：Handler基类
- `net.server.channel.handlers` 包：所有游戏内Handler
- `net.server.login.handlers` 包：登录阶段Handler

## 四、登录流程与数据包

### 4.1 完整登录交互时序

```
Client                          LoginServer                     ChannelServer
  │                                 │                               │
  │──── TCP连接到8484 ────────────►│                               │
  │◄─── 发送Hello包(版本+IV种子)────│                               │
  │                                 │                               │
  │──── 发送登录账号密码 ──────────►│                               │
  │◄─── 登录结果(成功/失败) ────────│                               │
  │                                 │                               │
  │──── 请求服务器列表 ────────────►│                               │
  │◄─── 返回世界/频道列表 ──────────│                               │
  │                                 │                               │
  │──── 选择频道 ─────────────────►│                               │
  │◄─── 返回频道IP:Port + 玩家ID ──│                               │
  │                                 │                               │
  │──── 断开登录服连接 ────────────│                               │
  │                                 │                               │
  │──── TCP连接到频道端口 ───────────────────────────────────────►│
  │◄─── 频道Hello包 ──────────────────────────────────────────────│
  │                                 │                               │
  │──── 发送玩家ID登录 ───────────────────────────────────────────►│
  │◄─── 返回玩家角色列表 ──────────────────────────────────────────│
  │                                 │                               │
  │──── 选择角色/PIC码验证 ───────────────────────────────────────►│
  │◄─── 登录成功，进入游戏世界 ────────────────────────────────────│
  │                                 │                               │
  │──── 游戏内数据包交互 ─────────────────────────────────────────►│
  │◄─── 各种游戏状态更新 ──────────────────────────────────────────│
```

### 4.2 登录阶段关键数据包详解

#### 4.2.1 Hello包（服务端→客户端）

客户端刚建立TCP连接后，服务端第一个发送的包，用于协商加密IV。

**SendOpcode**: 无（这是特殊包，不经过常规Opcode路由）

**包结构**：
| 长度 | 类型 | 说明 |
|------|------|------|
| 2 byte | short | 版本号（83） |
| 2 byte | short | 补丁版本（WzVersion，通常1） |
| 4 byte | byte[] | 服务端发送IV（4字节） |
| 4 byte | byte[] | 服务端接收IV（4字节） |
| 1 byte | byte | 区域标识 |

客户端收到Hello包后，使用收到的IV初始化本地加密上下文，之后所有包都使用协商好的IV加解密。

---

#### 4.2.2 登录请求（客户端→服务端）

**RecvOpcode**: `LOGIN_PASSWORD = 0x01`

**包结构**：
| 类型 | 说明 |
|------|------|
| byte | 0x01 (Opcode) |
| string | 用户名 |
| string | 密码 |
| ... | 其他客户端信息 |

---

#### 4.2.3 登录结果（服务端→客户端）

**SendOpcode**: `LOGIN_STATUS = 0x00`

**登录成功**：
| 类型 | 说明 |
|------|------|
| short | 0x00 (Opcode) |
| byte | 0x00 (成功状态码) |
| int | 账号ID |
| byte | 性别 |
| byte | GM等级 |
| byte | 账号标志 |
| int | 点数值 |
| ... | 更多账号信息 |

**登录失败**：
| 类型 | 说明 |
|------|------|
| short | 0x00 (Opcode) |
| byte | 错误码（3=密码错误, 4=账号不存在, 5=封号等） |
| byte | 错误消息长度 |
| string | 错误消息（如"您输入的密码不正确"） |

常见错误码：
- 0x00: 登录成功
- 0x03: 密码错误
- 0x04: 账号不存在或已删除
- 0x05: 账号已登录/被封号
- 0x07: 版本不匹配
- 0x08: 账号被封禁

---

#### 4.2.4 服务器列表（服务端→客户端）

**SendOpcode**: `SERVERLIST = 0x02`

客户端请求服务器列表后，服务端返回所有世界（World）和频道（Channel）信息。

**包结构**：
| 类型 | 说明 |
|------|------|
| short | Opcode (0x02) |
| byte | 世界数量 |
| 循环: | 每个世界: |
| - byte | 世界ID |
| - string | 世界名称 |
| - byte | 频道数量 |
| - 循环: | 每个频道: |
| -- string | 频道名称 |
| -- int | 频道负载（人数，显示在列表） |
| -- byte | 世界ID |
| -- byte | 频道ID |
| -- short | 成年/未成年标志 |
| - string | 世界说明 |
| ... | 其他配置 |

---

#### 4.2.5 选择频道（客户端→服务端）

**RecvOpcode**: `SERVERLIST_REREQUEST = 0x04` 或 `CHARLIST_REQUEST = 0x05`

客户端选择某个频道后发送。

服务端回复 **SERVER_IP (0x07)** 包，包含频道服务器地址和端口，以及一个一次性登录key：

**SendOpcode**: `SERVER_IP = 0x07`
| 类型 | 说明 |
|------|------|
| short | Opcode (0x07) |
| short | 固定0x0000填充 |
| byte | IP地址长度（4） |
| byte[4] | IP地址（如127.0.0.1 = [127,0,0,1]） |
| short | 端口号 |
| int | 角色登录ID（登录频道用的key） |
| byte[5] | 填充字节 |

---

### 4.3 频道登录阶段

客户端收到频道地址后：
1. 断开与LoginServer的连接
2. 建立到ChannelServer的新TCP连接
3. 进行频道连接握手和角色登录

#### 4.3.1 频道Hello包

和登录阶段类似，新连接建立后，ChannelServer首先发送Hello包，协商频道阶段的加密IV（与登录阶段IV不同）。

#### 4.3.2 角色列表（服务端→客户端）

**SendOpcode**: `CHARLIST = 0x04`

**包结构**：
| 类型 | 说明 |
|------|------|
| short | Opcode (0x04) |
| byte | 角色数量（最多6个） |
| 循环: | 每个角色: |
| - byte | 角色槽位 |
| - string | 角色名 |
| - string | 性别（"0"/"1"） |
| - byte | 皮肤颜色 |
| - int | 脸型 |
| - int | 发型 |
| - long | 宠物ID1 |
| - long | 宠物ID2 |
| - byte | 等级 |
| - short | 职业 |
| - short | 力量/敏捷/智力/运气 |
| - ... | 其他外观数据 |
| - short | 公会ID（无公会为0） |
| - ... | 装备外观信息 |
| int | 剩余角色槽位 |
| int | 可购买角色槽位 |

---

#### 4.3.3 选择角色进入游戏（客户端→服务端）

**RecvOpcode**: `PLAYER_LOGGEDIN = 0x0A`（具体Opcode看版本）

客户端选择角色并输入PIC码（如果启用）后发送。

服务端验证通过后，发送一系列初始化包：
1. `SET_FIELD` / `WARP_TO_MAP` (0x7E)：切换到角色所在地图
2. `SPAWN_PLAYER` (0xA0)：生成玩家自己
3. 背包数据初始化包
4. 技能数据包
5. 好友/公会/组队数据
6. 怪物刷新、NPC生成
7. 其他玩家进入视野的生成包
8. ... 大量初始化数据包

此时客户端正式进入游戏世界，可以开始操作。

## 五、选频道/选角色流程

### 5.1 服务器选择界面流程

登录成功后，客户端显示服务器选择界面（世界选择→频道选择）：

1. **世界选择**：显示所有可用世界（如"冒险岛"、"测试区"等）
   - 每个世界可以有多个频道
   - 世界列表由服务端 `SERVERLIST` 包发送

2. **频道选择**：选择某个世界后，显示该世界下所有频道
   - 频道显示负载（人数条）
   - 推荐频道标注
   - 维护中频道不可选

3. **进入角色选择**：
   - 客户端发送选频道包
   - 收到 `SERVER_IP` 后断开登录服
   - 连接到对应频道服
   - 进入角色选择界面

### 5.2 角色选择流程

频道连接成功后进入角色选择界面：

1. **角色列表展示**：
   - 显示该账号下所有角色（最多6个或更多）
   - 展示角色外观（穿着装备预览）
   - 显示等级、职业、名字
   - 可删除角色（需验证PIC码/生日）

2. **创建新角色**：
   - 点击"创建角色"按钮
   - 选择职业类型（冒险家/骑士团等）
   - 自定义性别、发型、脸型、皮肤、衣服
   - 输入角色名（需验证是否重复）
   - 发送创建角色包，成功后新角色出现在列表

   **RecvOpcode**: `CREATE_CHAR = 0x09` (或类似)
   **SendOpcode**: `CREATE_CHAR_RESPONSE = 0x0E`
   - 0x00 = 创建成功
   - 其他值 = 名字已存在/名字非法/职业不允许等

3. **删除角色**：
   - 选择角色点击"删除"
   - 输入PIC码/生日验证
   - 发送删除包
   - 服务端返回结果（可能有冷静期，如30秒内可恢复）

4. **进入游戏**：
   - 双击角色或点"选择"
   - 输入PIC码（如果启用了二次密码）
   - 发送登录角色包
   - 服务端加载角色数据，初始化游戏世界
   - 客户端进入游戏界面

### 5.3 二次密码（PIC）系统

PIC（Personal Identification Code）是登录角色时的二次密码，增强账号安全：

- 登录时需要输入6位左右的PIC码
- PIC密码错误多次会临时限制
- 在Web后台或游戏内可修改PIC
- 部分服务端可配置是否启用PIC

PIC验证在 `CHAR_SELECT_WITH_PIC` 或类似Handler中处理。

## 七、如何抓包分析

### 7.1 抓包工具选择

分析冒险岛网络协议常用以下工具：

| 工具 | 用途 |
|------|------|
| **WPE Pro (Winsock Packet Editor)** | Windows下经典封包抓取/修改工具，适合直接抓取客户端进程数据包 |
| **Wireshark** | 通用网络抓包工具，可抓取网卡流量，配合过滤器使用 |
| **Charles/Fiddler** | 代理抓包（主要HTTP，但也可抓TCP） |
| **本地日志** | 修改服务端/客户端代码打印收发数据包日志（最方便开发调试） |
| **MapleShark** | 冒险岛专用抓包工具，自动识别Opcode解析包结构（需对应版本定义） |

**推荐**：开发阶段直接在服务端代码中打印数据包日志最方便。

### 7.2 服务端开启数据包日志

在服务端代码中，可以在PacketDecoder/PacketProcessor处添加日志，打印收发的所有数据包：

1. 找到 `net.PacketProcessor` 类，在处理包入口添加日志：
   ```java
   public void handlePacket(InPacket in, Client client) {
       short opcode = in.readShort();
       // 打印日志
       if (LOGGER.isDebugEnabled()) {
           byte[] data = in.getData();
           LOGGER.debug("Recv [{}]: {}", String.format("0x%04X", opcode), Hex.encodeHexString(data));
       }
       // 路由到Handler...
   }
   ```

2. 在 `net.packet.PacketEncoder` 编码处加日志，打印发送的包：
   ```java
   // 在encode/write方法中，包加密前打印
   LOGGER.debug("Send [{}]: {}", String.format("0x%04X", opcode), Hex.encodeHexString(body));
   ```

3. 配置logback.xml，将日志级别设为DEBUG：
   ```xml
   <logger name="org.gms.net" level="DEBUG" />
   ```

**注意**：数据包日志量很大，仅开发调试时开启，生产环境务必关闭。

### 7.3 使用Wireshark抓包

1. 启动Wireshark，选择正在使用的网卡
2. 设置捕获过滤器：
   ```
   port 8484 or port 8500 or portrange 8484-8700
   ```
3. 启动客户端执行操作
4. 使用Wireshark的TCP流追踪功能查看数据流：
   - 右键一个包 → Follow → TCP Stream
   - 但因为数据是加密的，Wireshark只能看到密文，看不到明文

**因此**：如果要分析明文协议内容，最佳方式是在客户端/服务端解密之后打印日志，或者使用WPE这类进程级Hook工具。

### 7.4 WPE Pro抓包方法

1. 启动WPE Pro
2. 选择目标进程（MapleStory客户端）
3. 点击"Start Logging"开始抓包
4. 在客户端执行你想分析的操作（如点击NPC、攻击）
5. 点击停止，查看捕获的数据包列表
6. 每个包可以看到发送/接收方向、原始字节
7. 需要自己根据Opcode定义解密和解析包结构

### 7.5 分析未知数据包

遇到未实现的功能（未知Opcode）时，分析步骤：

1. **触发动作**：在客户端执行特定操作（如点击某个按钮）
2. **抓包对比**：抓取点击前后的数据包
3. **定位Opcode**：找出点击时新出现的包，其前1-2字节就是Opcode
4. **字段猜测**：
   - 反复改变操作参数（如选不同物品），对比包的差异
   - 识别字符串字段（2字节长度前缀）
   - 识别int/short等数值字段
   - 识别ID类字段（物品ID、怪物ID、地图ID可在WZ中查到）
5. **验证**：在服务端添加对应空Handler，读取字段打印出来，看是否符合预期
6. **实现**：解析字段并编写业务逻辑，发送正确的响应包

### 7.6 常见ID查询

分析数据包时需要经常查询各种ID：

| ID类型 | 说明 | 位置 |
|--------|------|------|
| 地图ID | int，如射手村100000000 | wz/Map.wz/Map/Map.img.xml |
| 怪物ID | int，如蜗牛 0100100 = 100100 | wz/Mob.wz |
| NPC ID | int，如希娜 1002000 | wz/Npc.wz |
| 物品ID | int，各物品ID定义 | wz/String.wz/Item.img.xml |
| 技能ID | int，各职业技能 | wz/Skill.wz/String.img.xml |
| 任务ID | int | wz/String.wz/Quest.img.xml |

物品ID段划分（参考）：
- 武器：130xxxx, 140xxxx...
- 防具：100xxxx（帽子）、105xxxx（套服）、106xxxx（手套）等
- 消耗品：200xxxx（药水）、207xxxx（飞镖）、233xxxx（卷轴）
- 其他：300xxxx（矿石）、400xxxx（任务物品）
- 现金物品：500xxxx

## 八、如何添加新的RecvOpcode/SendOpcode

### 8.1 添加RecvOpcode（客户端包处理器）

当需要处理一个新的客户端数据包时，按以下步骤添加：

#### 步骤1：在RecvOpcode中添加常量

找到 `net.opcodes.RecvOpcode` 文件，添加Opcode常量：

```java
public final class RecvOpcode {
    // ... 已有操作码 ...
    
    // 示例：添加一个"新功能操作"
    public static final short NEW_FEATURE_ACTION = 0x123;  // 根据抓包得到实际值
}
```

**注意**：Opcode值必须和客户端发送的完全一致，否则无法路由。

#### 步骤2：创建PacketHandler类

在 `net.server.channel.handlers` 包（或login/map包，根据阶段）创建新的Handler类，继承 `AbstractPacketHandler`：

```java
package org.gms.net.server.channel.handlers;

import org.gms.net.AbstractPacketHandler;
import org.gms.net.packet.InPacket;
import org.gms.client.Client;

public class NewFeatureHandler extends AbstractPacketHandler {
    
    @Override
    public void handlePacket(InPacket in, Client c) {
        // 1. 读取数据包字段（按照协议顺序读取）
        byte type = in.readByte();
        int itemId = in.readInt();
        String name = in.readString();
        
        // 2. 校验玩家是否登录、在游戏中
        if (c.getPlayer() == null) {
            return;
        }
        
        // 3. 业务逻辑处理
        // ... 你的功能代码 ...
        
        // 4. 发送响应包（如需返回给客户端）
        // c.announce(PacketCreator.newFeatureResponse(...));
    }
    
    @Override
    public boolean validateState(Client c) {
        // 返回true表示该Handler需要已登录状态
        return c.isLoggedIn();
    }
}
```

#### 步骤3：注册Handler到PacketProcessor

找到 `net.PacketProcessor` 类，在初始化注册Handler的地方注册新Handler：

```java
// 在registerHandlers() 或类似初始化方法中添加：
registerHandler(RecvOpcode.NEW_FEATURE_ACTION, new NewFeatureHandler());
```

**注意**：不同阶段（登录、频道、商店等）使用不同的PacketProcessor实例，要注册到正确的处理器中：
- 登录阶段Handler注册到 `loginProcessor`
- 游戏频道Handler注册到 `channelProcessor`
- 现金商城Handler注册到 `cashshopProcessor`

#### 步骤4：如果需要响应包，在PacketCreator中添加方法

找到 `tools.PacketCreator`（或对应的发送包工具类），添加发送包构建方法：

```java
public static byte[] newFeatureResponse(boolean success, String message) {
    OutPacket out = new OutPacket();
    out.writeShort(SendOpcode.NEW_FEATURE_RESPONSE);
    out.writeBool(success);
    out.writeString(message);
    // 写入其他返回字段...
    return out.getBytes();
}
```

然后在Handler中调用 `c.announce(PacketCreator.newFeatureResponse(true, "操作成功"));` 发送给客户端。

### 8.2 添加SendOpcode（服务端主动发包）

如果需要服务端主动发送新类型数据包给客户端：

#### 步骤1：在SendOpcode中添加常量

```java
public final class SendOpcode {
    // ...
    public static final short NEW_FEATURE_RESPONSE = 0x456;
}
```

同样，值必须和客户端期望的Opcode一致。

#### 步骤2：在PacketCreator中添加构建方法

如上面步骤4所示，使用OutPacket按协议顺序写入各字段。

#### 步骤3：在业务逻辑中调用发送

- 单个玩家：`c.announce(packetData);` 或 `player.announce(packetData);`
- 地图内所有玩家：`map.broadcastMessage(packetData);`
- 特定玩家附近：`map.broadcastMessage(player, packetData);`
- 全服所有玩家：`World.Broadcast.broadcastMessage(packetData);`
- 某个频道：`channel.broadcastMessage(packetData);`

### 8.3 注意事项

1. **Opcode匹配**：服务端和客户端的Opcode必须完全一致，版本变更时客户端Opcode可能改变，要同步更新服务端。

2. **字段顺序**：读写顺序必须严格和客户端一致，先写的必须先读，否则会导致整个包解析错位。

3. **异常处理**：Handler中要做参数校验，避免畸形包导致服务端异常。
   ```java
   if (in.available() < EXPECTED_LENGTH) {
       LOGGER.warn("Packet too short for NewFeature");
       return;
   }
   ```

4. **线程安全**：Handler是在Netty IO线程执行的，耗时操作（数据库查询、复杂计算）应提交到业务线程池，避免阻塞网络线程。

5. **日志**：开发阶段多打印日志，方便调试：
   ```java
   LOGGER.debug("NewFeature: type={}, itemId={}, name={}", type, itemId, name);
   ```

6. **状态验证**：重写 `validateState` 方法，确保操作时玩家处于合法状态（如不能在死亡时使用攻击技能）。

7. **反外挂校验**：对于战斗、物品操作等敏感Handler，务必添加合法性校验，防止客户端篡改包数据作弊。

```java
void writeBytes(byte[] data);     // 写字节数组
void writeZero(int count);        // 写入count个0字节
byte[] getBytes();                // 获取构建好的数据包字节数组
```

## 总结

冒险岛v83网络协议的核心要点：
1. **TCP长连接**，自定义二进制协议
2. **双层加密**：CustomEncryption加密包头，AES-OFB加密包体
3. **IV初始化**：连接建立时Hello包协商IV，之后IV随包变化
4. **Opcode路由**：每个包有Opcode标识，分发到对应Handler处理
5. **小端序**：所有数值都是小端序排列
6. **两阶段连接**：先登录服验证、获取频道地址，再连接频道服进入游戏

掌握以上内容后，你就可以开始添加新的数据包处理、开发新功能了。建议参考现有Handler的写法，保持代码风格一致。
